# Prior art (1998–2010) for capturing and restoring thread/continuation state by program transformation on the JVM and CLR

Scope note: citation metadata (authors, title, venue, pages, DOI) was checked against Crossref (api.crossref.org) and Semantic Scholar. DBLP (Anubis bot wall), SpringerLink (auth redirect) and web.archive.org could not be reached from this environment, so no Springer abstracts were read directly. Mechanism claims come from primary PDFs where one could be downloaded (Stadler 2009, Srinivasan & Mycroft 2008, Pettyjohn et al. 2005, Loitsch 2007, Bouchenak et al. INRIA RR-4662). Otherwise they come from survey papers, and each such claim is marked "(secondary)".

**Important finding for the whitepaper, and a possible conflict with the brief.** Dave Hillier's own 2015 description of the Second Life rewriter shows a **flag/return-based** unwind: an `IsSaving` flag, `goto Yield`, then `PushFrame` and a normal return. It does not describe an exception-based one. See the "Second Life" section. The whitepaper's authors should confirm which mechanism the shipped system used. Both mechanisms have JVM precedents from 1998–2001.

## Q1. JavaGo (Sekiguchi, Masuhara, Yonezawa): what it did and exact citation

### Takeaway
JavaGo (COORDINATION 1999) is a **source-to-source** Java translator. It captures the stack by **throwing an exception that each frame catches, saving its state into a chain of State objects and rethrowing**. It restores by re-invoking methods and jumping to the saved point through switch/case "unfolding", because Java source has no goto. A 2001 follow-up by the same group describes the exception-handling technique in general form (Java and C++, defined on bytecode). This group is the clearest early source of technique (a) together with (b).

### Cited Findings
- Citation (verified via Crossref): Tatsurou Sekiguchi, Hidehiko Masuhara, Akinori Yonezawa. "A Simple Extension of Java Language for Controllable Transparent Migration and its Portable Implementation." In *Coordination Languages and Models* (COORDINATION 1999), LNCS 1594, Springer, 1999, pp. 211–226. DOI 10.1007/3-540-48919-3_16 — [Crossref/DOI](https://doi.org/10.1007/3-540-48919-3_16); [Semantic Scholar](https://api.semanticscholar.org/graph/v1/paper/DOI:10.1007/3-540-48919-3_16)
- Mechanism (secondary): "In JavaGo, strong mobility is provided by source code transformations. An exception mechanism is employed for capturing the execution state: exceptions are thrown recursively until the whole call stack is saved as a chain of State objects. Because Java does not include a goto statement, these transformations must resort to switch-case statements. This requires some pre-processings (including splitting expressions with side effects) and unfolding techniques. An `undock` statement marks the part of the code that will be migrated. At restart, unfolding techniques must be also used for loops." — [Milanés, Rodriguez, Schulze, "Heterogeneous Strong Computation Migration", arXiv cs/0612125](https://arxiv.org/pdf/cs/0612125)
- Follow-up with the general technique (verified via Crossref): Tatsurou Sekiguchi, Takahiro Sakamoto, Akinori Yonezawa. "Portable Implementation of Continuation Operators in Imperative Languages by Exception Handling." In *Advances in Exception Handling Techniques*, LNCS 2022, Springer, 2001, pp. 217–233. DOI 10.1007/3-540-45407-1_14. Semantic Scholar lists the year as 2000, but the volume was published in 2001. — [DOI](https://doi.org/10.1007/3-540-45407-1_14)
- Pettyjohn et al. (ICFP 2005) summarise Sekiguchi et al. 2001 as follows. It is "a method for implementing partial continuations in Java and C++, with check-pointing and thread migration as possible applications. The method uses exception handling to construct continuation values as the stack unwinds." The translation is "defined on byte-codes" and includes a fragmentation step similar to A-normalisation. "During resumption an extra parameter carries the control state and extra logic is added to each function to distinguish between normal function calls and resumption." It uses Gunter et al.'s `cupto`/`set` delimited-continuation operators. Pettyjohn et al. also note that Sekiguchi et al. identify, but do not solve, the problem of non-transformed frames on the stack. — [Pettyjohn et al., "Continuations from Generalized Stack Inspection", ICFP 2005, DOI 10.1145/1086365.1086393](https://doi.org/10.1145/1086365.1086393)
- Loitsch (Scheme Workshop 2007) describes the exception-based suspend/resume technique as developed by "Tao (Tao 2001) and Sekiguchi et al. (Sekiguchi et al. 2001). In both cases the technique has been developed for transparent migration and checkpointing, and uses Java/JVM and/or C++ as target-language." He also says "Their work does not present full fledged continuations but only a way of suspending and resuming executions." — [Loitsch, "Exceptional Continuations in JavaScript", Scheme and Functional Programming Workshop 2007](http://www.schemeworkshop.org/2007/procPaper4.pdf) [URL not checked; the paper text was read from a local PDF]
- A performance comparison in Bouchenak et al. classes JavaGo as "application-level", portable but not complete. In their recursive-Fibonacci benchmark JavaGo showed roughly 246–250% execution overhead, against roughly 189–193% for Brakes and 88–89% for JavaGoX. — [Bouchenak, Hagimont, Krakowiak, De Palma, Boyer, INRIA RR-4662, Dec 2002](https://inria.hal.science/inria-00071923/document)

### Inferences
- JavaGo (1999) already combines both techniques the whitepaper describes: (a) per-frame catch, save and rethrow to build a frame chain, and (b) re-invocation with dispatch to a saved program point. It works at Java source level. The 2001 paper applies the same technique at bytecode level.

### Gaps
- The 1999 and 2001 Springer PDFs were not read directly because Springer was blocked. The JavaGo mechanism is confirmed by two independent secondary sources (Milanés et al.; Pettyjohn et al.) and one tertiary one (Loitsch).

## Q2. Brakes (Truyen et al., ASA/MA 2000): mechanism and citation

### Takeaway
Brakes is a **bytecode transformer** (KU Leuven). Capture works by **explicit return-and-check**: each method saves its frame into a per-thread Context object and returns, recursively. It does **not** use exceptions. Restore re-invokes the methods and uses bytecode `goto` to reach the "last performed instruction". Brakes is the lineage that Apache Commons Javaflow grew out of.

### Cited Findings
- Citation (verified via Crossref): Eddy Truyen, Bert Robben, Bart Vanhaute, Tim Coninx, Wouter Joosen, Pierre Verbaeten. "Portable Support for Transparent Thread Migration in Java." In *Agent Systems, Mobile Agents, and Applications* (ASA/MA 2000), LNCS 1882, Springer, 2000, pp. 29–43. DOI 10.1007/978-3-540-45347-5_4 — [DOI](https://doi.org/10.1007/978-3-540-45347-5_4). The LNCS volume number 1882 comes from memory and was not confirmed through Crossref's output; the pages and DOI were confirmed.
- Mechanism (secondary): "The serialization of Java threads in the Brakes framework is achieved through the instrumentation of bytecode… In the state capture state, every method saves the current frame in the Context object and returns to the previous method recursively until the end of the stack is reached. Given that the instruction counter is not available in Java, a counter was created to represent the 'last performed instruction' (LPI). On recovery, the thread restores the first frame from the context stack… and moves the program counter to the saved LPI (using the goto instruction, available only at bytecode level)… the method will be called and it will recover its frame from the context… State verification is done by code inserted automatically by the bytecode transformer at the beginning of every invoked method." — [Milanés et al., arXiv cs/0612125](https://arxiv.org/pdf/cs/0612125)
- A search-result summary of the Brakes project page describes it as "a ByteCode transformer that instruments Java classfiles so they are able to capture their current internal state at any given time… without requiring modifications to the Java Virtual Machine". The page now redirects to the author's Distrinet page, so this was not read directly. — [Brakes project page (redirects)](https://people.cs.kuleuven.be/~eddy.truyen/BRAKES/brakes.html)
- Hillier names Brakes and JavaGoX as the influences on the Second Life rewriter. — [Hillier, "IIRC: Second Life Mono internals", 2015](https://davehillier.net/2015/03/11/second-life-mono-internals/)

### Inferences
- Brakes is the closest precedent to the Second Life mechanism *as Hillier describes it*: flag-driven save on return, frames pushed to a per-thread context, and a restore prologue that dispatches to a saved index.

### Gaps
- The Brakes paper itself was not read directly (Springer and archive.org blocked). The exact flag names (e.g. `isSwitching` / `isRestoring`) are not confirmed here.

## Q3. Other JVM thread-migration and persistence work: Fünfrocken, Sakamoto (JavaGoX), Wei Tao, Bouchenak, Illmann

### Takeaway
Fünfrocken (1998, WASP) was the first to use exceptions in a Java **source preprocessor**, inserting try/catch to save state. Sakamoto, Sekiguchi and Yonezawa (JavaGoX, 2000) moved the JavaGo approach to **bytecode**, using a bytecode type system to recover operand-stack and local types. Wei Tao's 2001 Utah PhD thesis defined an exception-based shutdown/restart transformation at both **source and bytecode** level. Bouchenak and Illmann took the opposite, VM-level route (a modified JVM, and the JPDA debugger interface respectively).

### Cited Findings
- **Fünfrocken** (verified via Crossref): Stefan Fünfrocken. "Transparent Migration of Java-Based Mobile Agents." In *Mobile Agents* (MA '98), LNCS 1477, Springer, 1998, pp. 26–37. DOI 10.1007/BFb0057646 — [DOI](https://doi.org/10.1007/BFb0057646). The LNCS number 1477 is from memory and was not confirmed. A journal version was also found: S. Fünfrocken, "Transparent migration of Java-based mobile agents: Capturing and re-establishing the state of Java programs", *Personal Technologies* 2(2):109–116, June 1998, DOI 10.1007/BF01324941 — [DOI](https://doi.org/10.1007/BF01324941)
- Fünfrocken mechanism (secondary): "Fünfrocken proposes a similar approach for saving and restoring the state of Java programs, using exception handling. A compiler inserts try-catch statements in the source code to save the state of execution of each thread in different Java backup objects. On restart, all the threads… are restarted by creating new threads which will be initialized with the contents of their respective saved counterparts." Migration is subjective only, at explicit points (`allowGo`). — [Milanés et al., arXiv cs/0612125](https://arxiv.org/pdf/cs/0612125). Bouchenak et al. list the system as "Wasp", application-level. — [INRIA RR-4662](https://inria.hal.science/inria-00071923/document)
- **Sakamoto / JavaGoX** (verified via Crossref): Takahiro Sakamoto, Tatsurou Sekiguchi, Akinori Yonezawa. "Bytecode Transformation for Portable Thread Migration in Java." In *Agent Systems, Mobile Agents, and Applications* (ASA/MA 2000), LNCS 1882, Springer, 2000, pp. 16–28. DOI 10.1007/978-3-540-45347-5_3 — [DOI](https://doi.org/10.1007/978-3-540-45347-5_3)
- JavaGoX approach (from search-result summaries of the Springer abstract): "does not need extended virtual machines nor source code of target programs. The whole state of stack frames is saved and then restored at a remote site, using a type system for Java bytecode to correctly determine valid frame variables and operand stack entries." — [Springer page (search snippet)](https://link.springer.com/chapter/10.1007/978-3-540-45347-5_3)
- The claim that JavaGoX "uses exception handlers to navigate the stacks", saving operand-stack values into extra locals because a handler clears the operand stack, appeared only in a search-engine summary with no traceable primary source. **UNVERIFIED.** It is consistent with the same group's 2001 exception-handling paper (which has Sakamoto as co-author and a bytecode-level translation, per Pettyjohn et al.).
- Kilim's authors note the operand-stack cost of exception-based unwinding: exceptions "clear the operand stack as well. This unnecessarily forces one to take a snapshot of the operand stack before making a call." — [Srinivasan & Mycroft, ECOOP 2008 PDF](https://www.malhar.net/sriram/kilim/kilim_ecoop08.pdf)
- **Wei Tao**: Wei Tao. "A portable mechanism for thread persistence and migration." - Tao mechanism (from Pettyjohn et al.): "Like Sekiguchi et al., Tao describes a method for thread persistence and migration, leveraging Java's exception mechanism. Tao defines the translation for source code and byte-codes." Pettyjohn et al. also say Tao "maintains an index and adds extra logic to the code so that the resumption point can be relocated when a continuation is reinstated". They note that Tao "essentially makes two versions of the program: a shutdown version and a restart version". For source-level translation, Tao forbids capture during expression evaluation. There is only a skeletal proof and no correctness theorem. — [Pettyjohn et al. ICFP 2005](https://doi.org/10.1145/1086365.1086393)
- **Bouchenak**: S. Bouchenak, D. Hagimont. "Pickling threads state in the Java system." Proc. TOOLS 33 (Technology of Object-Oriented Languages and Systems), IEEE, 2000, pp. 22–32. DOI 10.1109/TOOLS.2000.848748 — [DOI](https://doi.org/10.1109/TOOLS.2000.848748). Also S. Bouchenak, D. Hagimont, S. Krakowiak, N. De Palma, F. Boyer. "Experiences implementing efficient Java thread serialization, mobility and persistence." *Software: Practice and Experience* 34(4):355–393, 2004. - Bouchenak mechanism: the JVM itself is extended. "The Java Virtual Machine is extended to capture the state of a Java thread as an object and to initialize a thread with a particular state," using type inference and dynamic de-optimisation. The LNCS number is from memory and was not confirmed. The system is called "CIA" and uses JPDA to read and restore state. Simão et al. note that JPDA-based solutions "are only able to extract the state of a single thread." — [Simão, Garrochinho, Veiga, CCPE 2011, DOI 10.1002/cpe.1879](https://sites.fct.unl.pt/synergy-vm/files/2012._crm-oo-vm_ccpe.pdf)
- Related VM-level work found in passing: JESSICA2 (Zhu, Wang, Lau, IEEE Cluster 2002, pp. 381–388, DOI 10.1109/CLUSTR.2002.1137770) and Mobile JikesRVM (Quitadamo, Cabri, Leonardi, *Sci. Comput. Program.* 70:221–240, 2008, DOI 10.1016/j.scico.2007.07.009). Both modify the VM. — [Crossref](https://doi.org/10.1109/CLUSTR.2002.1137770)

### Inferences
- By 2001, three independent groups had published exception-based unwinding with per-frame save plus re-entry and dispatch for Java: Fünfrocken (1998, source), Sekiguchi et al. (1999 source, 2001 bytecode) and Tao (2001, source and bytecode). Brakes (2000) published the return-flag alternative at bytecode level. The individual *techniques* of the Second Life system therefore cannot be claimed as novel. Defensible contributions are more likely to be the application to the **CLR/CIL** (verifiable IL, value types, the .NET security sandbox) and the production scale. A further candidate is the combination with AppDomain-based unloading and inter-simulator migration of untrusted user code, with preemption via injected yield points on backward branches.

## Q4. Apache Commons Javaflow and RIFE continuations (mid-2000s)

### Takeaway
Javaflow (started around 2005 by Torsten Curdt, with roots in Brakes) and RIFE (Geert Bevin, around 2005–2007) are bytecode instrumentation frameworks. They use a flag-checked, return-based unwind into a thread-local parallel stack, not exceptions. Javaflow's `Continuation` is `java.io.Serializable`. RIFE continuations required the captured data to be cloneable or serializable and were limited to one frame (`processElement`).

### Cited Findings
- Javaflow `Continuation` API: "Snapshot of a thread execution state. A Continuation object is an immutable object that captures everything in the Java stack." The class implements `java.io.Serializable`. Authors listed are Stephan Michels and Torsten Curdt. — [Javaflow Continuation javadoc](https://commons.apache.org/sandbox/commons-javaflow/apidocs/org/apache/commons/javaflow/Continuation.html)
- Stadler et al. (2009) on Javaflow: "implements continuations without JVM support using bytecode instrumentation… All affected methods are modified such that they can distinguish between normal execution, continuation capturing, and continuation resuming, which adds runtime overhead even when no continuations are used. The local variables, expressions, and position are stored in a thread-local parallel stack. This approach is not tied to a specific Java virtual machine and allows continuations to be serialized." — [Stadler et al. PPPJ 2009 PDF](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf)
- Stadler et al. on RIFE: it "works similar to the Javaflow library, but it allows continuation capturing only within a specific method (processElement), so that there is always only one activation frame per continuation." — [Stadler et al.](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf). Kilim's authors likewise say "RIFE does not handle nested pausable calls." — [Kilim ECOOP 2008](https://www.malhar.net/sriram/kilim/kilim_ecoop08.pdf)
- Javaflow history (secondary, from a search summary of the tascalate-javaflow / vsilaev sources): Javaflow was started in 2005 by Torsten Curdt. The discontinued Brakes research project "formed the roots for the Javaflow project", and Stephan Michels later rewrote the Brakes-derived parts. Kohsuke Kawaguchi and Eugene Kuleshov were early contributors. The project "never got out from Commons Sandbox". — [tascalate-javaflow](https://github.com/vsilaev/tascalate-javaflow); [Silaev blog 2016](https://vsilaev.com/2016/05/20/javaflow-fork-intro/). Curdt was blogging about Java continuations for Cocoon as early as 2003–2004. — [Curdt blog, 2004](https://vafer.org/blog/20040331171224/)
- RIFE (interview published 1 March 2007): at class-load time RIFE detects `pause()` calls and rewrites bytecode. "The continuations infrastructure maintains a parallel stack that references the actual data." A deep clone is taken at each continuation, and "the data structure must be cloneable or serializable". — [Artima, "Continuations in Java" (Venners & Sommers with Bevin), 2007](https://artima.com/lejava/articles/continuations.html). RIFE was also integrated with Terracotta for distributed continuations. — [Artima](https://www.artima.com/articles/distributed-web-continuations-with-rife-and-terracotta)
- Performance: Stadler et al. report that their VM-based implementation was "one to two orders of magnitude" faster than Javaflow. — [Stadler et al.](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf)

### Gaps
- The Apache Commons dormant-project page returned 404, so the exact first commit and sandbox dates were not verified from Apache sources.

## Q5. Kilim (Srinivasan & Mycroft, ECOOP 2008)

### Takeaway
Kilim's weaver rewrites `@pausable` methods to take an extra `Fiber` argument and unwinds by **return-and-check, explicitly rejecting exceptions** as about 100x more expensive. Each frame stores its PC, operand stack and locals in the Fiber. On re-entry, each method consults the Fiber and jumps to the resumption point. It is one-shot, and nothing in the paper claims the Fiber state is serializable.

### Cited Findings
- Citation (verified via Crossref): Sriram Srinivasan, Alan Mycroft. "Kilim: Isolation-Typed Actors for Java." In *ECOOP 2008 – Object-Oriented Programming*, LNCS 5142, Springer, 2008, pp. 104–128. DOI 10.1007/978-3-540-70592-5_6 — [DOI](https://doi.org/10.1007/978-3-540-70592-5_6). The LNCS number 5142 is from memory and was not confirmed.
- Mechanism: "Each pausable method's signature is transformed to include an extra argument called a fiber… When the callee pauses… the caller examines the fiber, learns that it is now in a pausing state, stores its activation frame on the fiber and returns… The process is easily reversed: each method consults the fiber upon entry, jumps directly to the resumption point and restores its state where necessary." The authors call it "conceptually equivalent to a CPS transformation… produces single-shot" continuations. — [Kilim ECOOP 2008 PDF](https://www.malhar.net/sriram/kilim/kilim_ecoop08.pdf)
- On exceptions: "Some researchers have used exceptions as a longjmp mechanism to unwind the stack; we use return because we found exceptions to be more expensive by almost two orders of magnitude. Not only do they have to be caught and re-thrown at each level of the stack chain, they clear the operand stack as well." — [Kilim ECOOP 2008](https://www.malhar.net/sriram/kilim/kilim_ecoop08.pdf)
- Kilim criticises Pettyjohn et al. because their approach "relies on exceptions for stack unwinding, it creates custom objects per invocation site, splits the code into top-level procedures". — [Kilim ECOOP 2008](https://www.malhar.net/sriram/kilim/kilim_ecoop08.pdf)
- The mechanics were covered in an earlier Srinivasan paper, "A Thread of One's Own" (2006). — [PDF](https://www.malhar.net/sriram/kilim/thread_of_ones_own.pdf). The full thesis is Cambridge TR UCAM-CL-TR-769. — [PDF](https://www.cl.cam.ac.uk/techreports/UCAM-CL-TR-769.pdf)

### Gaps
- "A Thread of One's Own" was not read, so its venue (believed to be a 2006 workshop) is unverified. Fiber serializability is not addressed in the ECOOP paper; treat Kilim as not supporting it.

## Q6. Stadler et al., "Lazy continuations for Java virtual machines" (PPPJ 2009)

### Takeaway
The citation is verified. The mechanism is **VM-level**: a modification of the HotSpot interpreter and client compiler in the Da Vinci Machine / MLVM project. It is **not** a program transformation. Frames are captured as raw byte copies, and serialization is not claimed.

### Cited Findings
- Citation (verified via Crossref): Lukas Stadler, Christian Wimmer, Thomas Würthinger, Hanspeter Mössenböck, John Rose. "Lazy continuations for Java virtual machines." In *Proc. 7th International Conference on Principles and Practice of Programming in Java* (PPPJ 2009), ACM, 2009, pp. 143–152. DOI 10.1145/1596655.1596679 — [DOI](https://doi.org/10.1145/1596655.1596679)
- Affiliations as printed on the paper: Stadler, Würthinger and Mössenböck at "Johannes Kepler University Linz, Austria"; **Wimmer at "University of California, Irvine"** (not JKU); Rose at "Sun Microsystems, Inc." — [PDF](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf)
- "We developed our implementation as an extension to the Java HotSpot VM… part of a larger effort… called the Da Vinci Machine Project or Multi-Language Virtual Machine Project (MLVM)." The activation `data` field "stores a plain copy of the stack contents of the activation frame". The system imposes "zero run-time overhead as long as no activations need to be saved and restored". — [PDF](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf)
- Related work in the paper covers Ovm (Dragoș et al.), Javaflow, RIFE, Ruby 1.9 copy-all, BCD Scheme (exception-based one-shot) and Chez Scheme segmented stacks. It does **not** cite JavaGo, Brakes, Tao or Kilim. — [PDF](https://ssw.jku.at/Research/Papers/Stadler09/Stadler09a.pdf)

### Inferences
- Stadler et al. is useful in the whitepaper as a contrast. A VM-level approach avoids per-method overhead but gives up portability and serializability, which Second Life needed to preserve across simulators.

## Q7. .NET/CLR work: Mono.Tasklets, published CLR migration work, and public material on Second Life's Mono migration

### Takeaway
Mono.Tasklets (from Tomi Valkeinen's MonoCo, 2006, shipped in Mono 2.6) is a **runtime-level stack-copy** continuation that is not portable to other CLIs and not serializable. Second Life's system was publicly presented at **Lang.NET 2006** (Jim Purbrick and Cory Ondrejka). Miguel de Icaza described it in 2006 and 2009 as CIL rewriting that injects state serialization and "reincarnation", and it shipped to the main grid on 29 August 2008. Hillier's 2015 blog post is the most detailed public technical description. No peer-reviewed .NET program-transformation thread-migration paper from before 2008 turned up in these searches.

### Cited Findings
- Miguel de Icaza (7 June 2006): "Microthreading was necessary because some of their simulations are made up of thousand of threads/routines, and using the default threads in Mono… would have been too heavy… Their micro-threading implementation is different than Tomi's recent continuation work in that Second Life has added support to 'migrate' running code across machines." — [tirania.org, 2006-06-07](https://tirania.org/blog/archive/2006/Jun-07-1.html)
- Miguel de Icaza (9 April 2009, "Continuations in Mono: Embrace and Extending .NET, Part 3"): in 2006 Jim of Linden Lab presented Second Life's microthreading at Lang.NET. It used "a CIL rewriting engine that injected the state serialization and reincarnation into an existing CIL instructions stream." SL "required that code be suspended at any point in time and that its entire state be serializable into a format suitable for storage into a database." "The technology went in production in 2008 and today this continuation framework powers 10 million Mono scripts on SecondLife." Mono.Tasklets is based on Tomi Valkeinen's MonoCo, which modified the Mono runtime, and became part of Mono 2.6. — [tirania.org, 2009-04-09](https://tirania.org/blog/archive/2009/Apr-09.html)
- Mono docs: Mono.Tasklets exposes `Mark()`, `Store()` and `Restore()`, and "requires changes to the VM that are not portable to other ISO CLI implementations". — [Mono archived Continuations page](https://www.mono-project.com/archived/continuations/); microthreads library: [mono/mono-microthreads](https://github.com/mono/mono-microthreads)
- Jim Purbrick's blog: "Lang.NET 3 Years On" (27 April 2009) refers back to the 2006 talk with Cory Ondrejka. There is also a FOSDEM 2010 talk on Mono in Second Life, with video and slides, and "Another Age Must Be The Judge" (29 September 2010) on leaving Linden Lab. The 2006 work included "a new LSL compiler back end to generate CIL bytecode, a scavenging garbage collector to allow assembly unloading and a microthread injector to allow tens of thousands of scripts to run concurrently on Mono in a single process." — [jimpurbrick.com/tag/mono](https://jimpurbrick.com/tag/mono.html); [jimpurbrick.com/tag/second-life](http://jimpurbrick.com/tag/second-life.html). Other public material: SE Radio Episode 141, "Second Life and Mono with Jim Purbrick" — [YouTube](https://www.youtube.com/watch?v=BK-2YDbwubc); InfoQ "Mono LSL" (January 2007) — [InfoQ](https://www.infoq.com/news/2007/01/Mono-LSL); Babbage Linden's "Second Life In Mono" (August 2005) — [secondlife.blogs.com](https://secondlife.blogs.com/babbage/2005/08/second_life_in_.html)
- Deployment: Mono went live on the main grid on 29 August 2008 with server 1.24.3. Per-script memory was 64 KB under Mono against 16 KB under LSL2. — [SL Wiki "Mono"](https://wiki.secondlife.com/wiki/Mono)
- Hillier (2015), primary technical description. "The stack serialisation was achieved by modifying the program's byte code that inserted blocks do the capture and restore of the current threads state. Doing it at the code level meant that we did not have to modify Mono and the code could also be ported to a standard Windows .Net VM." "The assembly rewriter was implemented using RAIL, which is similar to Mono Cecil." "At the start of each method, a block of code is injected to do the restore. It get the saved frame and restores the local variables and the state of the stack. It then jumps to the part of the method that was previously executed. At the end of the method it inserts code to do the save which populates a stack frame. At various points within the method, it injects yield points." "Backwards jump is one of the places to insert a yield." The pseudocode shows `if (IsRestoring) { var frame = PopFrame(); switch(frame.pc) {...goto PCn} }`, and at a yield `if (IsYieldDue) { frame.pc=1; frame.locals=...; frame.stack=...; goto Yield; }` followed by `Yield: if (IsSaving) PushFrame(frame); // return normally`. Other points in the post: migration also moved scripts between AppDomains (nursery and long-lived) to allow unloading; only the LSL compiler's subset of CIL was supported; and it cites Brakes and JavaGoX as influences. — [davehillier.net, 2015-03-11](https://davehillier.net/2015/03/11/second-life-mono-internals/)

### Inferences
- **Conflict with the research brief:** the only public technical description, Hillier's pseudocode, shows a Brakes/Kilim-style **flag-and-return unwind** (`IsSaving`, `PushFrame`, "return normally"), not per-frame exception handlers that rethrow. The pseudocode may be a simplification, or the shipped system may have differed. The whitepaper authors should confirm against the original source before claiming an exception-based unwind. If exceptions were used, the closest prior art is JavaGo, Sekiguchi 2001 and Tao 2001. If flags were used, it is Brakes, Javaflow and Kilim.
- RAIL ("Runtime Assembly Instrumentation Library", University of Coimbra, around 2005–2006) was the CIL rewriting tool used. Its citation was not verified in this pass.
- Second Life's system was presented publicly (Lang.NET 2006) about two years before Kilim (ECOOP 2008) and Stadler (PPPJ 2009). Its publicly documented production deployment of transformation-based serializable continuations on the CLR (August 2008) appears to have no earlier .NET counterpart in these searches.
